# c_vis v0.4 — Browser-first C Visualizer

## Product contract

Give c_vis a C file or project folder. c_vis analyzes it, builds it, runs it under native GDB, captures execution, and lets the user explore the run without configuring debugger/build internals.

## Architecture

```text
Browser
├── file/folder ingestion
├── project source store
├── static project analysis (Web Worker)
├── trace store
├── First / Previous / Next / Last replay
├── source navigation
├── snapshot diff / visualization
├── client telemetry
└── diagnostics UI
        │
        │ project upload + NDJSON trace stream
        ▼
Execution backend
├── workspace validation/materialization
├── build-plan validation/inference
├── native compile / make
├── executable detection
├── adapter/profile selection
├── GDB execution + inspection
├── structured logs / metrics
└── structured errors
```

## Responsibility boundary

### Browser owns
- file/folder selection and drag/drop
- source contents after import
- source tree and navigation
- lightweight static analysis
- `main()` discovery
- build-system hints
- project/profile hints
- execution trace history
- timeline cursor and replay
- stdout/operation reconstruction
- visualization and state diffing
- client telemetry and local diagnostics

### Backend owns
- safe workspace creation
- build-plan verification
- compilation
- executable selection
- native process execution
- GDB/MI
- debugger timeouts and cancellation
- runtime snapshots
- server telemetry and health

## Trace protocol

Runs use an NDJSON response stream. The backend emits events instead of owning replay state.

```text
run.started
build.started
build.completed
snapshot
snapshot
...
run.completed | run.cancelled | trace.limit | error
```

Snapshot events contain runtime state plus only the *new* stdout/operation data since the previous state. The browser reconstructs cumulative output. This removes cumulative output duplication across thousands of snapshots.

## Error model

Every operational failure has:

```text
code
stage
message
retryable
requestId
runId (when applicable)
details (safe diagnostics only)
```

Stages: `ingest`, `workspace`, `build`, `debugger`, `trace`, `client`, `server`.

Expected failures are rendered as product states, not raw HTTP/GDB exceptions.

## Observability

### Server
- JSON structured logs
- request/run/workspace IDs
- counters for requests, workspaces, builds, runs, snapshots and errors
- duration aggregates for workspace/build/run stages
- process uptime/memory diagnostics
- `/api/health`
- `/api/diagnostics`

### Browser
- import/analyze/upload/run timings
- captured client errors and unhandled rejections
- trace event/snapshot counters
- bounded in-memory event buffer
- optional telemetry forwarding without source contents
- diagnostics drawer

## v0.4 supported project shapes

1. Single `.c` file.
2. Simple multi-file C project without a build system.
3. Makefile project.
4. `push_swap` remains an enhanced profile, not a debugger-core dependency.

## Explicit v0.4 boundaries

- no arbitrary dependency/package installation
- no hosted execution
- no generic heap reconstruction yet
- no full CMake/Meson/autotools support
- no source editing
- no guarantee that every Makefile can be debug-rebuilt automatically

## Acceptance criteria

- User can select/drop a C file or folder without Docker volume configuration.
- Browser identifies C files, headers, `main()`, Makefile presence and supported profile.
- Backend creates an isolated disposable workspace from the uploaded project.
- Supported projects build with debug symbols without a user-provided shell command.
- Execution trace streams to the browser as it is produced.
- First/Previous/Next/Last and slider are local browser operations after states arrive.
- Browser source browsing does not call `/api/source`.
- Cumulative stdout/operation arrays are not duplicated in every streamed snapshot.
- `push_swap` trace rules are outside the generic GDB client.
- Structured diagnostics identify the stage and correlation ID for failures.
