# c_vis v0.4 — Browser-first C Visualizer

## Product contract

> Give c_vis C code and it takes care of the rest.

The user supplies C source. c_vis decides whether the code should be **executed** or **structurally visualized**. The absence of `main()` or executable behavior is not an error condition.

## Mode resolution

```text
C input
  ↓
Browser analysis
  ↓
Executable behavior?
  ├── main() exists
  │     ↓
  │   runtime visualization
  │
  ├── function definitions exist
  │     ↓
  │   generated disposable runner
  │     ↓
  │   runtime visualization
  │
  └── no executable function
        ↓
      static source visualization
```

The user never configures GDB, debug flags, executable paths, Docker mounts, adapter settings, or a synthetic `main()`.

## Responsibility boundary

### Browser owns
- file/folder selection and drag/drop
- source contents after import
- source tree and navigation
- project analysis
- runtime-vs-static mode decision
- static declaration visualization
- `main()` discovery
- callable-function discovery and parameter defaults
- semantic entry-function selection when needed
- build-system hints
- project/profile hints
- execution trace history
- timeline cursor and replay
- stdout/operation reconstruction
- visualization and state diffing
- client telemetry and local diagnostics

### Backend owns — runtime mode only
- safe workspace creation
- entry-point verification
- disposable runner generation when no `main()` exists
- build-plan verification
- compilation
- executable selection
- native process execution
- GDB/MI
- debugger timeouts and cancellation
- runtime snapshots
- server telemetry and health

Static-only inputs do not need to be uploaded to the execution backend.

## Runtime entry-point resolution

```text
main() exists?
  ├── yes → build/run program normally
  └── no
       ↓
  detect function definitions
       ↓
  one function? ── yes → select automatically
       │
       └── several → select a default + expose semantic choice
       ↓
  infer argument defaults
       ↓
  generate __cvis_harness.c in disposable runtime
       ↓
  compile + break directly at selected source function
```

The generated harness never modifies uploaded source. GDB starts at the selected source function rather than presenting generated infrastructure as part of the learning experience.

## Static source visualization

If no executable function exists, c_vis renders a structural model immediately in the browser.

Current v0.4 static model:

- structs and fields
- source location for each declaration
- self-referential pointer detection
- linked-structure candidate visualization
- enums and members
- simple typedef aliases
- object-like `#define` constants

The Memory view and execution timeline are disabled because no runtime memory/state exists. The code pane remains active and structural elements navigate back to source.

If the source contains neither executable behavior nor a supported structural declaration, c_vis shows an explicit static empty state rather than a build/debug error.

## Trace protocol

Runtime runs use an NDJSON response stream. The backend emits events instead of owning replay state.

```text
run.started
build.started
build.completed
snapshot
snapshot
...
run.completed | run.cancelled | trace.limit | error
```

Snapshot events contain runtime state plus only the new stdout/operation data since the previous state. The browser reconstructs cumulative output.

## Error model

Operational runtime failures have:

```text
code
stage
message
retryable
requestId
runId (when applicable)
details (safe diagnostics only)
```

Stages: `ingest`, `workspace`, `build`, `debugger`, `trace`, `client`, `server`.

`NO_EXECUTABLE_CODE` is no longer a normal user-facing outcome for static inputs; static mode handles that case before runtime execution is requested.

## Observability

### Server
- JSON structured logs

- selected entry kind/name without source contents
- counters for requests, workspaces, builds, runs, snapshots and errors
- duration aggregates for workspace/build/run stages
- process uptime/memory diagnostics

### Browser
- import/analyze/upload/run timings
- runtime/static mode decision
- detected declaration counts
- selected entry kind/function

- optional telemetry forwarding without source contents
- diagnostics drawer

## v0.4 supported input shapes

1. Single `.c` file with `main()`.
2. Single `.c` file containing function definitions but no `main()`.
3. Simple multi-file C project, with or without `main()`.
4. Header/type-only C input for static visualization.
5. Non-executable `.c` source containing supported declarations.
6. Makefile application project.
7. `push_swap` as an enhanced runtime profile.

## Explicit v0.4 boundaries

- no arbitrary dependency/package installation
- no hosted execution
- no generic heap reconstruction yet
- no full CMake/Meson/autotools support
- no source editing
- no guarantee that every third-party/custom Makefile dependency can be reconstructed automatically
- static analysis currently recognizes a bounded set of C declaration forms; unsupported syntax remains visible in the source pane even when no specialized visual model exists

These are capability boundaries, not user configuration requirements.

## Acceptance criteria

- User can select/drop C source without Docker volume configuration.
- Browser identifies C files, headers, functions, `main()`, structs, enums, aliases, constants and supported profile hints.
- Browser selects runtime or static visualization automatically.
- A project with `main()` runs normally.
- A project without `main()` but with a callable function runs through a generated disposable runner.
- A project with no runnable function becomes a static visualization rather than an execution error.
- Header-only structural input never requires compile/GDB execution.
- Function parameters receive useful defaults and can be changed without editing source.
- Generated harness code is never presented as the user's source execution surface.
- Runtime trace streams to the browser as it is produced.
- First/Previous/Next/Last and slider are local browser operations after states arrive.
- Static mode has no execution timeline and disables runtime-memory controls.
- Browser source browsing does not call `/api/source`.
- Cumulative stdout/operation arrays are not duplicated in every streamed snapshot.
- `push_swap` trace rules are outside the generic GDB client.
- Structured diagnostics identify the stage and correlation ID for failures.
