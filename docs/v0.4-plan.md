# c_vis v0.4 — Browser-first C Visualizer

## Product contract

> Give c_vis C code and it takes care of the rest.

The user supplies a C file or project folder. c_vis analyzes it, resolves how execution should start, builds it, runs it under native GDB, captures execution, and lets the user explore the run without configuring debugger/build internals.

`main()` is not a user requirement. If a normal program entry point exists, c_vis uses it. If it does not, c_vis detects callable function definitions and generates a disposable runner in the execution workspace. When several functions are valid entry points, c_vis selects one by default and exposes the function choice because that is semantic user intent, not build/debug configuration.

## Entry-point resolution

```text
C input
  ↓
main() exists?
  ├── yes → build/run program normally
  └── no
       ↓
  detect function definitions
       ↓
  one function? ── yes → select automatically
       │
       └── several → select a sensible default + expose choice
       ↓
  infer safe argument defaults
       ↓
  user changes only semantic inputs that matter
       ↓
  generate __cvis_harness.c in disposable runtime
       ↓
  compile + break directly at selected source function
```

The generated harness never modifies uploaded source. GDB starts at the selected source function rather than presenting the generated runner as part of the learning experience.

For ordinary scalar and pointer parameters c_vis supplies initial C-expression defaults (`0`, `0.0`, `""`, etc.). More complex values can be entered as C expressions. If a signature or project cannot be built automatically, c_vis returns build diagnostics instead of requiring the user to configure GDB or a shell command.

## Trace protocol

Runs use an NDJSON response stream. The backend emits events instead of owning replay state.

```text
run.started
build.started
build.completed
snapshot
snapshot
...
run.completed | run.cancelled | trace.limit | error
```

Snapshot events contain runtime state plus only the *new* stdout/operation data since the previous state. The browser reconstructs cumulative output. This removes cumulative output duplication across thousands of snapshots.

## Error model

Every operational failure has:

```text
code
stage
message
retryable
requestId
runId (when applicable)
details (safe diagnostics only)
```

Stages: `ingest`, `workspace`, `build`, `debugger`, `trace`, `client`, `server`.

Entry-specific failures include `ENTRYPOINT_REQUIRED`, `ENTRYPOINT_NOT_FOUND`, and `NO_EXECUTABLE_CODE`. Expected failures are rendered as product states, not raw HTTP/GDB exceptions.

## v0.4 supported project shapes

1. Single `.c` file with `main()`.
2. Single `.c` file containing function definitions but no `main()`.
3. Simple multi-file C project, with or without `main()`.
4. Makefile application project.
5. `push_swap` remains an enhanced profile, not a debugger-core dependency.

For mainless projects the generated-harness path uses c_vis's debug compiler path. Projects that rely on custom external link dependencies may still surface a structured build failure rather than silently guessing missing dependencies.

## Explicit v0.4 boundaries

- no arbitrary dependency/package installation
- no hosted execution
- no generic heap reconstruction yet
- no full CMake/Meson/autotools support
- no source editing
- no guarantee that every third-party/custom Makefile dependency can be reconstructed automatically
- runtime visualization requires at least one actual C function definition; declarations/types alone have no execution to trace

These are execution-environment boundaries, not user configuration requirements. c_vis does not hand GDB/build configuration back to the user.

## Acceptance criteria

- User can select/drop a C file or folder without Docker volume configuration.
- Browser identifies C files, headers, functions, `main()`, Makefile presence and supported profile.
- A project with `main()` runs normally.
- A project without `main()` but with a callable function can be visualized through a generated disposable runner.
- Function parameters receive useful defaults and can be changed without editing source.
- Generated harness code is never presented as the user's source execution surface.
- Backend creates an isolated disposable workspace from the uploaded project.
- Supported projects build with debug symbols without a user-provided shell command.
- Execution trace streams to the browser as it is produced.
- First/Previous/Next/Last and slider are local browser operations after states arrive.
- Browser source browsing does not call `/api/source`.
- Cumulative stdout/operation arrays are not duplicated in every streamed snapshot.
- `push_swap` trace rules are outside the generic GDB client.
- Structured diagnostics identify the stage and correlation ID for failures.
