# c_vis v0.5 — Final Visualization Architecture

## Product goal

> c_vis takes C code, determines how to inspect it, and turns its structure and execution into an understandable visual model.

v0.5 finalizes visualization. The runtime truth remains generic; the presentation becomes deliberately human-readable.

## Canonical model

```text
C source + execution position
          ↓
Native execution / GDB
          ↓
Generic runtime truth
├── call frames
├── locals / arguments
├── addressable arrays / structs
├── referenced objects
├── subobject addresses
└── pointer relationships
          ↓
┌──────────────────────┬────────────────────────┐
│ Program              │ Memory                 │
│ human projection     │ canonical C model      │
├──────────────────────┼────────────────────────┤
│ arrays               │ stack frames           │
│ strings              │ local storage          │
│ linked lists         │ referenced memory      │
│ stacks               │ exact types/addresses  │
│ queues               │ pointer targets        │
│ trees                │ subobject aliases      │
│ object graphs        │ call-stack ownership   │
└──────────────────────┴────────────────────────┘
          ↓
Browser-owned replay timeline
```

## Runtime truth model

Every paused snapshot can expose:

- multiple call frames, not only the selected frame
- arguments and locals per frame
- scalar and enum values
- arrays with indexed elements
- structs and unions with fields
- addresses for roots, fields, and array elements
- pointers and NULL
- C strings when readable
- address-stable referenced objects
- pointer relationships
- safe unreadable-pointer states

Address identity is stable across snapshots. Inspection is bounded by depth, object count, array length, string length, and frame count. Cycles are detected by address identity.

## Program view

Program answers:

> What does this data mean to a human?

The best-fit projection is used when c_vis can classify the runtime shape:

- scalar → value tile
- char array / string → readable string + indexed characters
- array → indexed horizontal cells
- singly linked chain → linked-list stage
- `top` / stack vocabulary + recursive chain → vertical stack
- `front` / `rear` / queue vocabulary + recursive chain → queue channel
- two recursive child pointers → tree canvas
- arbitrary pointer-rich structure → node-edge object graph
- struct / union → readable field card

Addresses remain available as secondary detail/tooltips rather than dominating the Program view.

## Memory view

Memory answers:

> How does C represent this state?

The canonical view separates:

- Stack: each call frame is a visual container for its own variables
- Stack-owned arrays and structs: rendered inside the owning frame
- Heap / referenced memory: objects reached through pointers and not proven to be frame-owned
- References: pointer source → resolved destination

Subobject addresses allow aliases to resolve to human paths when possible. Example:

```text
reverse_string.str → main.greeting[1]
```

rather than only:

```text
str → 0x7ffd...
```

c_vis does not label an address as allocator-owned heap memory unless that ownership is known; the column deliberately says **Heap / referenced**.

## State transitions

Adjacent snapshots are diffed in the browser. Visuals distinguish:

- object created
- object removed
- object changed
- scalar changed
- pointer target changed

Stable addresses are visual identities so unchanged nodes stay visually stable while insertions, removals, and pointer changes animate around them.

## Adapter boundary

The generic runtime inspector owns C fundamentals.

Adapters may add domain meaning, but are not responsible for basic traversal of pointers, structs, arrays, frames, or referenced objects.

`push_swap` therefore keeps its specialized A/B stack projection while generic Memory still comes from the runtime truth model.

## Acceptance

v0.5 is accepted when generic runtime visualization can represent and replay:

- scalar values
- integer arrays
- C strings / char arrays
- pointer into a local array/subobject
- structs and nested structs
- pointer-to-struct values
- singly linked lists
- stacks
- queues
- binary-tree-shaped structures
- NULL pointers
- cyclic structures without unbounded traversal
- arbitrary pointer graphs through the graph fallback
- multiple call frames with local ownership
- push_swap without regressing its specialized Program view

Automated validation includes runtime graph/classification tests, frame/subobject resolution tests, GDB Python syntax, Svelte production build, Docker build, native C execution, linked-list runtime capture, and a nested-call char-array integration trace.
