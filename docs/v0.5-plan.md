# c_vis v0.5 — Semantic Runtime Visualization

## Product goal

> c_vis takes C code, determines how to inspect it, and turns its structure and execution into an understandable visual model.

v0.5 finalizes the visualization layer. It does not add a new project workflow; it makes the existing v0.4 execution trace explain arbitrary C state instead of falling back to debugger strings.

## Runtime pipeline

```text
Native C execution
      ↓
GDB
      ↓
Generic runtime inspector
      ↓
Value Graph
      ↓
Browser snapshot diff
      ↓
Structure classifier
      ↓
Semantic projection
      ↓
Svelte Program / Memory views
```

## Runtime truth model

Every paused snapshot can expose:

- current-frame roots: arguments and locals
- scalar and enum values
- arrays with bounded elements
- structs and unions
- pointers and NULL
- C strings when readable
- address-stable objects
- pointer relationships
- safe unreadable-pointer states

Inspection is bounded by depth, object count, array length, and string length. Cycles are detected by address identity.

## Browser projections

The browser classifies the generic value graph into:

- scalar
- string
- array
- struct / union
- linked list
- tree
- pointer
- generic object graph fallback

Classification is structural. Field names such as `next`, `left`, and `right` can reinforce meaning but the underlying pointer/type relationship remains authoritative.

## State transitions

Adjacent snapshots are diffed in the browser. The visual layer distinguishes:

- object created
- object removed
- object changed
- scalar changed
- pointer target changed

Stable runtime addresses are used as visual identities so unchanged objects remain stable across replay states.

## Program vs Memory

**Program** answers: what is the program doing?

It uses semantic layouts such as linked chains, trees, arrays, strings, and object cards.

**Memory** answers: how does this exist in C memory?

It shows roots, exact types, addresses, fields, pointer targets, reachable objects, and the call stack.

## Adapter boundary

The generic runtime inspector is independent of adapters.

Adapters such as `push_swap` may add domain semantics, but they are not responsible for basic pointer, struct, array, or object traversal.

## Acceptance

v0.5 is accepted when the generic runtime path can visually represent:

- scalar values
- arrays
- strings
- structs and nested structs
- pointer-to-struct values
- singly linked lists
- binary-tree-shaped structures
- NULL pointers
- cyclic structures without unbounded traversal
- arbitrary pointer graphs through the fallback object view
- push_swap without regressing its specialized Program view

Automated validation includes runtime-graph unit tests, GDB Python syntax, Svelte production build, Docker build, and a native linked-list C integration trace.
